# How it works

## What it reads

1. **Effective sshd config.** Runs `sshd -T`, which resolves `Include` directives and prints every effective keyword with its final value. Plain `sshd -T` prints the configuration with **no `Match` block applied**, and gives no hint that any exist, so the tool also runs `sshd -T -C user=<account>` once per account (see item 3) to pick up that account's effective `AuthorizedKeysFile` from any `Match User` or `Match Group` block that changes it. That is the only setting taken from the per-account run. Criteria that depend on an actual connection (`Match Address`, `LocalPort`, and the rest) cannot be evaluated without one, so `sshd` treats them as not matching and this tool sees the same thing. If that per-account run itself fails, the tool falls back to the global `AuthorizedKeysFile` for the accounts it failed for, and says so in a single coverage warning that names every one of them.

   If `sshd -T` fails (no `sshd` binary, not root, or the config is broken) the tool falls back to parsing `/etc/ssh/sshd_config` directly, following its `Include` directives the way `sshd` does: each one is expanded where the line sits rather than at the end, a relative path is taken as relative to `/etc/ssh`, and the files a pattern matches are read in sorted order. Nothing in `/etc/ssh/sshd_config.d` is read when there is no `Include` naming it, because `sshd` does not read it either. Each line's arguments are split the way `sshd` splits them (`argv_split()` in `misc.c`): a `#` that starts an argument ends the line, while a `#` inside an argument is an ordinary character; single and double quotes group text, so an argument can hold a space; a backslash outside quotes escapes a quote, another backslash, or a space; and a line with a quote that is never closed is skipped, because `sshd` would refuse the whole configuration over it. A keyword may be separated from its value by an `=` as well as by whitespace, with spaces allowed on either side of it, so `StrictModes=no`, `StrictModes = no`, and `StrictModes =no` all mean the same thing; only one `=` is ever skipped, and it is the one that ends the keyword, so `StrictModes==no` has the value `=no`, which `sshd` itself refuses. A `Match` line opens a block whatever else is wrong with it — an unclosed quote, or no argument at all — because reading the block's body as global configuration would be far worse than skipping it: the block's `AuthorizedKeysFile` would become the global pattern and no account's real file would ever be scanned. Tilde expansion is applied to `AuthorizedKeysFile` and `HostKey` arguments as `sshd` applies it — a leading `~`, whether it stands alone or is followed by `/`, to the home directory of the account running the audit, which stands in for the account running `sshd`, normally root, and `~name` to that named account's home directory — and a relative `HostKey` path is made absolute against the directory the audit is running in, which stands in for the directory `sshd` was started in. `Match` blocks are skipped entirely, and the first occurrence of each keyword is the one used — so a drop-in included near the top of the file beats a value set further down in the file itself. The fallback cannot see fully-expanded algorithm lists either, so those checks are skipped and a coverage warning says both things.

   `sshd -T` validates the whole configuration before printing anything, so when it fails, its stderr is itself useful: bad host-key permissions, missing host keys, and syntax errors all show up there. The tool surfaces that text in the coverage warning.

2. **Host keys.** Every `HostKey` directive, or the OpenSSH defaults when none is set. `HostKey none` is a sentinel `sshd` keeps as an empty entry rather than the name of a file — `derelativise_path()` hands the literal `none` back, `fill_default_server_options()` clears the entry, `sshd` skips it when it loads host keys, and `sshd -T` prints it as `hostkey (null)` — so neither spelling is looked for on disk; when it is the only `HostKey` set, `sshd` has no host key at all and exits with `no hostkeys available -- exiting` (verified against OpenSSH 10.2), which is reported as a finding in its own right. Each of the rest is fingerprinted from the public half stored inside the private key file, which is readable without the passphrase and whatever the file's permissions are. A `.pub` file sitting next to the key is only compared against that: if the two disagree, the `.pub` file is reported as stale, and the private key's own answer is the one used. Keys in the old PEM formats carry no readable public half, so for those the private key file itself is fingerprinted first — by pointing `ssh-keygen -l` at a symlink to it inside a throwaway, private temporary directory, because asking `ssh-keygen -l` for the file in place would silently answer from any `.pub` file sitting beside it instead of reading the private key at all. The `.pub` file is used only when `ssh-keygen` cannot read the private file at all — most often because it is passphrase-protected, or because it is owned by the account running the tool with any group or other permission bits set (`ssh-keygen` refuses to open such a key — any bit, not just a read bit, so mode 0601 and mode 0610 are turned down as surely as 0644 is; a key owned by someone else is read fine, so root auditing a user's world-readable key is not affected), or because the body is corrupt — and in that case a stale `.pub` cannot be detected, since there is nothing to compare it against. The `.pub` file is only ever read for a file that positively holds one of those old PEM or PKCS#8 headers, since those are the formats that cannot answer for themselves. A file whose format cannot be established — one the tool cannot read the bytes of at all (a root-owned host key on a non-root run, say), an empty file, or a file whose first line is not a private-key header — gets no `.pub` answer: nothing says the `.pub` beside it describes this key, and the report says the key could not be fingerprinted rather than naming a key it has not read. That is what keeps a zero-byte `ssh_host_ed25519_key` with a real `.pub` file next to it from being reported as a healthy Ed25519 host key. A key in the current OpenSSH format whose embedded public half cannot be read, or reads but cannot be fingerprinted, is corrupt, not merely an old format, and is reported as unfingerprintable no matter what `.pub` file sits beside it — that file could belong to a different key entirely. The whole file has to be intact and to hold exactly one key, not merely to have a readable public half. A file cut short after the public half, or carrying extra bytes after the private half, still yields a readable public key — `ssh-keygen -lf` even prints a fingerprint for either one — while a file missing its closing `-----END OPENSSH PRIVATE KEY-----` line, or claiming to hold two keys instead of one, is rejected outright (`ssh-keygen -lf` calls it "not a key file"). `ssh` and `sshd` load none of the four, so the report must not call any of them a healthy key. For an unencrypted key in the current format the private half is checked as well: `ssh-keygen` is asked to derive the public key from it (`ssh-keygen -y`, with an empty passphrase supplied so that it can never stop to ask for one), which is work only the private half can do, so no `.pub` file can answer for it. That runs `ssh`'s own loader over the file — the two check integers have to match, every private field has to deserialize, and the padding has to run 1, 2, 3, ... — so a key `ssh` cannot load is reported as unfingerprintable even when its public half reads perfectly. What that catches is any file `ssh`'s own loader cannot load: mismatched check integers, private fields that do not deserialize, bad padding, or a body mangled in transit (CRLF line endings, indentation). `ssh-keygen -l` cannot stand in for this: handed a private key file in the current format it answers from the public half inside it and mentions the private half's failure only in its debug output. A key gets only the checks on its public half, so corruption inside its private half is not detected, when it is passphrase-protected (it cannot be loaded without the passphrase), when `ssh-keygen` would refuse it over its permissions (the account running the tool owns it and it has any group or other permission bits set), or when the tool cannot stat it to tell which of those is the case. A `HostKey` that names a *public* key file is treated differently: `sshd` tries to load a private key from every `HostKey` and only then falls back to reading the file as a public key, so with `HostKeyAgent` set that is a working arrangement — `sshd` serves the key while the agent holds its private half — and the tool fingerprints and grades the key, says at INFO that the private half is out of its reach, and skips the permission, passphrase, and `.pub` checks, which are all about private key files. With no agent the entry is dead: verified against OpenSSH 10.2, `sshd` logs `Unable to load host key: <path>` and, with nothing else configured, exits with `no hostkeys available`, so the tool reports it at LOW, skips those same checks, does not count the key's type among the ones the host can actually offer, and does not grade its algorithm or size either — `sshd` never offers this key to anyone, so there is nothing about it for an attacker to reach. A `HostKey` naming a *certificate* file (`<name>-cert.pub`) is dead in the same way, and stays dead even with an agent: the fallback to the agent is only taken for a plain key type, so `sshd` logs `Unable to load host key` and exits with `no hostkeys available` whether an agent is configured or not — verified against OpenSSH 10.2 with a live agent holding both the host key and its certificate, where the plain `.pub` file loads and the `-cert.pub` file does not. That is reported at LOW, ungraded and uncounted, like a public key file with no agent; a certificate belongs on a `HostCertificate` line. A `HostKey` path the tool cannot even stat (permission denied on a directory above it, say) is reported as a LOW `could not stat host key` finding rather than being silently treated as missing.

3. **authorized_keys.** For every account returned by `getpwall()` (so NSS/LDAP accounts are included when the host resolves them), the tool asks `sshd -T -C user=<account>` for that account's own `AuthorizedKeysFile`, so a `Match User` or `Match Group` block that moves it (or sets it to `none`) is honoured. Each pattern is then expanded (`%h`, `%u`, `%U`, `%%`) and every existing file is scanned line by line. An `AuthorizedKeysFile` path containing a space is not supported: `sshd -T` prints the value with no quoting, and the fallback parser stores it the same way, so one path with a space in it cannot be told apart from two paths and is read as several. A file named by an absolute path with no `%u` in it is shared by every account — `sshd` consults it for all of them — so it is reported once per account, and its keys show up as reused across accounts. A key repeated for a single account — twice in one file, or once in each of two files that account uses — grants nobody any extra access, so it is noted separately at LOW rather than counted as reuse across accounts. Each line is split into options and key material — a line counts as option-less when its second field is a key blob naming the type in its first field, the same check `sshd` makes, so key types this tool has never heard of still parse — and the key material is passed to `ssh-keygen -lf -` for type, size, and fingerprint. Per-line invocation is slower than fingerprinting the whole file at once, but it is the only way to keep line numbers accurate when `sshd` would skip a malformed line. The options are then checked against the grammar `sshd` applies to them: the option names it knows, the `=` and the double quotes every value needs, the three clauses it accepts only once per line (`command=`, `principals=`, `from=`), the values given to `environment=` and `tunnel=`, and `principals=` only together with `cert-authority` (a principals list means nothing without a CA key to go with it, and `sshd` denies the line outright). A line that fails any of that is reported as rejected rather than counted as a working key, because `sshd` refuses the whole line when its options do not parse — so the key on it opens nothing, and it is left out of the reuse comparison as well. What is inside an `expiry-time=`, `permitopen=`, or `permitlisten=` value is not checked: whether those parse depends on the `sshd` version, on the machine's timezone and date handling, and on `/etc/services` lookups, and wrongly calling a working line dead would be worse than missing a broken one. An `sshd` that predates one of the option names in a file rejects that line too, which this tool cannot tell you — it knows the current set of names, not which of them the `sshd` on this host understands. A line whose own key blob is a certificate (`ssh-keygen -l` labels these `<TYPE>-CERT`) is reported as inert rather than graded, because `sshd` never matches a certificate blob against an `authorized_keys` line — see [findings.md](findings.md) for why. Such a line is kept out of the reuse comparison as well, because `ssh-keygen -l` reports a certificate under the fingerprint of the key it certifies, so counting it would make that key look as though it were authorised twice. A file the tool cannot even stat — another account's home when this tool is not running as root, for instance — is reported as a LOW `could not stat` finding rather than silently treated as absent.

4. **Private keys.** Every regular, non-symlink file directly in each account's `~/.ssh` that begins with a PEM or OpenSSH private-key header. These are fingerprinted the same way as host keys: from the public half stored inside the private key file when there is one, with any `.pub` file next to it only compared against that; for old PEM keys, which carry no such public half, the private file itself is fingerprinted first (through the same symlink-in-a-throwaway-directory trick described for host keys above), and the `.pub` file is used only for a file that positively holds one of those old headers, and only when `ssh-keygen` cannot read the private file. A file in `~/.ssh` whose own bytes the tool cannot read is not audited at all: the header check that decides whether a file is a private key cannot confirm it, so the file is skipped silently rather than reported as unfingerprintable. As with host keys, a current-format key whose embedded public half cannot be read, or reads but cannot be fingerprinted, is corrupt and is reported as unfingerprintable, whatever `.pub` file happens to sit beside it — and, also as with host keys, the whole file has to be intact and not merely its public half, because `ssh` cannot use a key file that stops partway through. Also as with host keys, the private half of an unencrypted current-format key is checked too — `ssh-keygen` is asked to derive the public key from it, which runs `ssh`'s own loader, so any file that loader cannot load (mismatched check integers, private fields that do not deserialize, bad padding, or a body mangled in transit by CRLF line endings or indentation) is reported as unfingerprintable even when its public half reads fine. A key gets only the checks on its public half when it is passphrase-protected, when `ssh-keygen` would refuse it because the account running the tool owns it and it has any group or other permission bits set, or when the tool cannot stat it to tell which of those is the case. A corrupt key in the *old* PEM format is not detected the same way: there is no embedded public half to read in the first place, and an unencrypted-but-corrupt PEM body still makes `ssh-keygen` fail to read the private file directly, so a corrupt PEM body is still reported as whatever `.pub` file sits beside it, because only `ssh-keygen` could tell a corrupt PEM body apart from a passphrase-protected one, and it refuses to open a key file that the account running it owns and that has any group or other permission bits set. Whether a passphrase is set is decided by inspecting the file (the OpenSSH format embeds the cipher name; PEM uses a `Proc-Type` header; PKCS#8 uses a distinct `BEGIN` line) rather than by asking `ssh-keygen`, because `ssh-keygen` refuses to load a key file that the account running it owns and that has any group or other permission bits set — exactly the keys most worth reporting on. An account's `~/.ssh` that the tool cannot read (again, most often another account's when not running as root) is skipped rather than raising an error; the start-of-run warning already says other accounts' files are skipped in that case.

Every file read in items 2, 3 and 4 is also reported with the date it was last changed: its modification time, printed as `YYYY-MM-DD` in the server's local time zone, so it matches what `ls -l` and `stat` show on the same box. A symlinked file is dated by the file it points at, which is the one `sshd` reads. A file that is not there, or that the tool could not stat, has no date to report, and neither does an entry that names no file at all, such as a `(none)` host-key placeholder.

## What it does not read

The report's **coverage warnings** list these when they apply:

- **`AuthorizedKeysCommand`** (sssd, ec2-instance-connect, GitHub-backed helpers, etc.). Keys served by a command are not files and are not audited.
- **`TrustedUserCAKeys`** — certificate-based logins. The CA is a file, but the set of certificates it has signed is not visible from the server.
- **`HostKeyAgent`** — private host keys held by an agent. The agent, not the filesystem, holds them, so they cannot be read or graded here; a `HostKey` naming the matching public key file is still fingerprinted and graded, though one naming a certificate file is not, because `sshd` cannot load a host key from a certificate even through an agent (see item 2 above).
- **`PubkeyAuthentication no`** — everything in `authorized_keys` is inert.
- **`AuthorizedKeysFile none`** — no files are consulted.
- **`AuthorizedKeysFile is 'none' for <account>`** — a `Match` block sets `AuthorizedKeysFile none` for that one account, so `sshd` reads no `authorized_keys` files for it and neither does the tool.
- **`AuthorizedKeysFile mixes 'none' with other entries`** — the audit cannot see which behaviour the `sshd` on this host will apply after its next upgrade, so it flags the value. Every released `sshd` skips just the `none` entry and scans the others, and this audit does the same; OpenSSH's current development code rejects the whole configuration instead, so a future upgrade may stop `sshd` from starting. Worth knowing before an upgrade does it for you.

Other things out of scope by design:

- Per-key *age* — each key file's last-modified date is reported (see above), but an `authorized_keys` file carries no timestamp on the individual lines, so that date says when the file last changed, not when any one key was added or removed. Compare fingerprints against an inventory if you need that.
- Keys under `~/.ssh` subdirectories, or in locations that are not `~/.ssh` (only host keys and `AuthorizedKeysFile` paths are read from config).
- Weak-entropy detection (the 2008 Debian OpenSSL blocklist). Rare enough now that it is left to `ssh-vulnkey`-style tooling.
- Client-side config (`~/.ssh/config`, `known_hosts`).
- `Match` blocks that change anything other than `AuthorizedKeysFile` — for example a per-account `AuthorizedKeysCommand`, `TrustedUserCAKeys`, or `PubkeyAuthentication no`. Only the global values of those are checked.

## Safety

The tool only reads files. The external commands it runs are `ssh-keygen -l` (fingerprinting), `ssh-keygen -y` (asking whether `ssh` can load a private half, described in item 2 above), and `sshd -T` (a config dry-run that does not start a daemon). Nothing is modified. Every `ssh-keygen` call either has stdin closed or is handed its input directly, and the one call that loads a private half is given an empty passphrase with `-P ""`, so none of them can ever block on a passphrase prompt or pop up an `SSH_ASKPASS` dialog on the operator's screen. The text report escapes what it prints: a key's comment and its options come out of a file the audited account owns, so every character a terminal would act on rather than display — an ANSI or OSC escape sequence, and anything else Unicode classifies as a control, format or surrogate character, plus the line and paragraph separators U+2028 and U+2029 that some terminals and pagers break a line on — is shown as `\x1b`, `\u200b` or `\U000e0020` instead, and a comment cannot recolour the report, erase a line the operator has already read, or rewrite the terminal's window title. Private-use characters and unassigned code points are left alone: no terminal acts on either, and which code points count as unassigned comes from the Unicode tables built into the interpreter, so escaping those would make the same comment print one way under one Python version and another way under the next. A backslash already in the file is printed as it stands, so a comment holding the four characters `\x1b` as ordinary text looks the same in the report as an escaped escape character — the escaping is there to stop the terminal acting on what it is handed, not to let the report be turned back into the file's bytes. Ordinary non-ASCII text is printed as it stands, and `--json` output needs none of this, because JSON escapes those characters itself. A character stdout cannot encode at all (an ASCII locale — `LC_ALL=C` with Python's UTF-8 coercion turned off) is written as a backslash escape too, so the report runs to the end instead of stopping at the first non-ASCII key comment.
