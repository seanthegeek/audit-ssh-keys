# How it works

## What it reads

1. **Effective sshd config.** Runs `sshd -T`, which resolves `Include` directives and prints every effective keyword with its final value. Plain `sshd -T` prints the configuration with **no `Match` block applied**, and gives no hint that any exist, so the tool also runs `sshd -T -C user=<account>` once per account (see item 3) to pick up that account's effective `AuthorizedKeysFile` from any `Match User` or `Match Group` block that changes it. That is the only setting taken from the per-account run. Criteria that depend on an actual connection (`Match Address`, `LocalPort`, and the rest) cannot be evaluated without one, so `sshd` treats them as not matching and this tool sees the same thing.

   If `sshd -T` fails (no `sshd` binary, not root, or the config is broken) the tool falls back to parsing `/etc/ssh/sshd_config` directly, following its `Include` directives the way `sshd` does: each one is expanded where the line sits rather than at the end, a relative path is taken as relative to `/etc/ssh`, and the files a pattern matches are read in sorted order. Nothing in `/etc/ssh/sshd_config.d` is read when there is no `Include` naming it, because `sshd` does not read it either. `Match` blocks are skipped entirely, and the first occurrence of each keyword is the one used — so a drop-in included near the top of the file beats a value set further down in the file itself. The fallback cannot see fully-expanded algorithm lists either, so those checks are skipped and a coverage warning says both things.

   `sshd -T` validates the whole configuration before printing anything, so when it fails, its stderr is itself useful: bad host-key permissions, missing host keys, and syntax errors all show up there. The tool surfaces that text in the coverage warning.

2. **Host keys.** Every `HostKey` directive, or the OpenSSH defaults when none is set. Each is fingerprinted from the public half stored inside the private key file, which is readable without the passphrase and whatever the file's permissions are. A `.pub` file sitting next to the key is only compared against that: if the two disagree, the `.pub` file is reported as stale, and the private key's own answer is the one used. Keys in the old PEM formats carry no readable public half, so for those the `.pub` file is used instead. A key in the current OpenSSH format whose embedded public half cannot be read is corrupt, not merely an old format, and is reported as unfingerprintable no matter what `.pub` file sits beside it — that file could belong to a different key entirely. The whole file has to be intact and to hold exactly one key, not merely to have a readable public half. A file cut short after the public half, or carrying extra bytes after the private half, still yields a readable public key — `ssh-keygen -lf` even prints a fingerprint for either one — while a file missing its closing `-----END OPENSSH PRIVATE KEY-----` line, or claiming to hold two keys instead of one, is rejected outright (`ssh-keygen -lf` calls it "not a key file"). `ssh` and `sshd` load none of the four, so the report must not call any of them a healthy key.

3. **authorized_keys.** For every account returned by `getpwall()` (so NSS/LDAP accounts are included when the host resolves them), the tool asks `sshd -T -C user=<account>` for that account's own `AuthorizedKeysFile`, so a `Match User` or `Match Group` block that moves it (or sets it to `none`) is honoured. Each pattern is then expanded (`%h`, `%u`, `%U`, `%%`) and every existing file is scanned line by line. A file named by an absolute path with no `%u` in it is shared by every account — `sshd` consults it for all of them — so it is reported once per account, and its keys show up as reused across accounts. A key repeated for a single account — twice in one file, or once in each of two files that account uses — grants nobody any extra access, so it is noted separately at LOW rather than counted as reuse across accounts. Each line is split into options and key material — a line counts as option-less when its second field is a key blob naming the type in its first field, the same check `sshd` makes, so key types this tool has never heard of still parse — and the key material is passed to `ssh-keygen -lf -` for type, size, and fingerprint. Per-line invocation is slower than fingerprinting the whole file at once, but it is the only way to keep line numbers accurate when `sshd` would skip a malformed line. A line whose own key blob is a certificate (`ssh-keygen -l` labels these `<TYPE>-CERT`) is reported as inert rather than graded, because `sshd` never matches a certificate blob against an `authorized_keys` line — see [findings.md](findings.md) for why.

4. **Private keys.** Every regular, non-symlink file directly in each account's `~/.ssh` that begins with a PEM or OpenSSH private-key header. These are fingerprinted the same way as host keys: from the public half stored inside the private key file, with any `.pub` file next to it only compared against that, falling back to the `.pub` file for old PEM keys. As with host keys, a current-format key whose embedded public half cannot be read is corrupt and is reported as unfingerprintable, whatever `.pub` file happens to sit beside it — and, also as with host keys, the whole file has to be intact and not merely its public half, because `ssh` cannot use a key file that stops partway through. A corrupt key in the *old* PEM format is not detected the same way: there is no embedded public half to read in the first place, so a corrupt PEM body is still reported as whatever `.pub` file sits beside it, because only `ssh-keygen` could tell a corrupt PEM body apart from a passphrase-protected one, and it refuses to open a world-readable file. Whether a passphrase is set is decided by inspecting the file (the OpenSSH format embeds the cipher name; PEM uses a `Proc-Type` header; PKCS#8 uses a distinct `BEGIN` line) rather than by asking `ssh-keygen`, because `ssh-keygen` refuses to load a world-readable key — exactly the keys most worth reporting on.

## What it does not read

The report's **coverage warnings** list these when they apply:

- **`AuthorizedKeysCommand`** (sssd, ec2-instance-connect, GitHub-backed helpers, etc.). Keys served by a command are not files and are not audited.
- **`TrustedUserCAKeys`** — certificate-based logins. The CA is a file, but the set of certificates it has signed is not visible from the server.
- **`PubkeyAuthentication no`** — everything in `authorized_keys` is inert.
- **`AuthorizedKeysFile none`** — no files are consulted.
- **`AuthorizedKeysFile is 'none' for <account>`** — a `Match` block sets `AuthorizedKeysFile none` for that one account, so `sshd` reads no `authorized_keys` files for it and neither does the tool.

Other things out of scope by design:

- Key *age* — `authorized_keys` carries no timestamp. Compare fingerprints against an inventory if you need this.
- Keys under `~/.ssh` subdirectories, or in locations that are not `~/.ssh` (only host keys and `AuthorizedKeysFile` paths are read from config).
- Weak-entropy detection (the 2008 Debian OpenSSL blocklist). Rare enough now that it is left to `ssh-vulnkey`-style tooling.
- Client-side config (`~/.ssh/config`, `known_hosts`).
- `Match` blocks that change anything other than `AuthorizedKeysFile` — for example a per-account `AuthorizedKeysCommand`, `TrustedUserCAKeys`, or `PubkeyAuthentication no`. Only the global values of those are checked.

## Safety

The tool only reads files. The only external commands it runs are `ssh-keygen -l` (fingerprinting) and `sshd -T` (a config dry-run that does not start a daemon). Nothing is modified. All `ssh-keygen` calls have stdin closed so they can never block on a passphrase prompt.
